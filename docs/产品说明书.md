# Waker 产品说明书

> 本地数字员工平台 · 岗位化的 Agent 团队常驻在你的机器上
> 版本：0.1.0 · 协议：MIT · 内核：Pi（MIT）

---

## 一、产品概述

### 一句话定义

Waker 是一个**本地优先（local-first）的数字员工平台**：你把"岗位"写成一份可读可改的档案，平台把这份档案装配成一个人格化的 Agent，常驻在你的机器上，随时通过命令行、HTTP 接口、定时任务或 IM 通道接受指派并交付结果。

### 产品定位

| 维度 | 说明 |
|------|------|
| 形态 | 本地服务 + CLI + Web 看板（非 SaaS，数据不出机器） |
| 内核 | Pi Agent Kernel（内核极简：4 个工具、系统提示词 < 1000 token） |
| 外壳 | 自研薄外壳：只做三件事——**身份装配、策略下发、任务编目** |
| 边界 | 不重建已有的会话索引 / IM 接入 / 技能库；记忆中心另带一个**分人隔离版**（multi-pi-memory），知识库仍复用 |

### 设计哲学

**薄外壳 + 深复用。** 不在 Pi 之上再包一层重型运行时，而是通过 Pi 官方 Extension 机制注入能力；外壳每一行都可读可改。相比同类方案：

| 方案 | 结论 |
|------|------|
| QoderWake | 闭源商业产品，不可自托管、不可审计 |
| Octop（腾讯，MIT） | 外壳开源，核心引擎尚未开源（"开源壳 + 闭源内核"） |
| OpenClaw（MIT） | 完整产品形态，但本身建在 Pi 之上（12 万+ 行），直接下沉到底层更可控 |
| **Pi + Waker** | 全链路 MIT；内核极简；外壳自研，每一行可读可改 |

### 与 Pie 的关系

本说明书参考开源项目 **Pie**（[github.com/s1dashu/pie](https://github.com/s1dashu/pie)，MIT，"Agent-to-IM 连接器"）的产品定义思路，并对齐以下关键概念：

- **一个 Agent 实例对应一份 Profile（岗位档案）**；
- **选择其背后的本地 Agent Harness（运行时框架）**，Waker 当前以 Pi 为默认且最稳定的 harness；
- **把 Agent 接入 IM 渠道**（飞书 / 微信 / Discord / 钉钉），在桌面端统观状态；
- **"把闭环做小而明确"**——渠道状态、运行时输出、日志、配置、密钥、技能与工作目录，一处可见。

差异在于：Pie 是 macOS 桌面应用（Electron），Waker 是**本地服务 + CLI + Web 看板**，更偏向"可脚本化、可版本化、可自托管"的工程取向。

**一个关键差异**：Pie 无法读取你本地已经创建好的 Pi agent / subagent；**Waker 可以**。Waker 会扫描 `~/.pi/agent/agents/*.md`，把既有的 agent / subagent profile 直接纳管为员工（只读），无需在平台内重建。详见 §4.7。

## 二、目标用户与典型场景

### 目标用户

- 需要**可审计、可自托管**自动化能力的工程师与团队；
- 希望把重复性工作（巡检、审校、简报、数据整理）交给一个**有岗位、有边界、有记忆**的 Agent；
- 不接受把敏感代码与凭据交给云端 SaaS 的团队。

### 典型场景

| 场景 | 员工岗位 | 触发方式 |
|------|----------|----------|
| 每日项目巡检 | `dailybot` | 定时（cron）/ 手动 |
| 代码变更审校 | `reviewer` | 手动 / 事件 |
| 变更简报与初诊 | `dailybot` | 定时 |
| 资料整理与归档 | 自定义 | API / IM |

## 三、核心概念

### 1. 员工（Waker / Agent Profile）

一个员工 = 一个目录 `agents/<id>/`，包含岗位元数据与五份档案：

```
agents/<id>/
├── waker.yaml     岗位元数据：职责、模型、工作目录、权限段
├── SOUL.md        人设总纲（最稳定：判断倾向、说话方式、底线）
├── identity.md    职责范围（我是谁、服务谁、接什么活）
├── persona.md     工作风格（先分析还是先动手、输出格式）
├── bible.md       红线与边界（禁止项、需人工确认的动作）
└── MEMORY.md      长期记忆（纳入 git，可回滚）
```

### 2. 身份装配（Identity Assembly）

身份文本在**外壳侧预编译**（不在运行时拼装），运行时纯内存命中——因为 `before_agent_start` 的 handler 串行 await，运行时拼装会成为性能瓶颈。

### 3. 安全门禁（Guard）

Pi 内核默认 YOLO（无条件执行工具调用）。Waker 补上三道防线：

1. **命令门禁**：前缀白名单 + 片段黑名单 + 高危人工确认；
2. **路径门禁**：目录白名单 + 凭据路径保护；
3. **执行隔离**：可选 Docker 容器，无外网、随容器销毁。

另有一个**默认关闭**的能力开关 `policy.selfEdit`：允许员工改自己的档案文本（人设/风格/红线/长期记忆），
但**权限不在可改范围**——它改不了 `waker.yaml`，所以无法自我扩权（见 §7.2）。

拦截点位于**工具替换层**（`bash` 同名覆盖），而非 `tool_call` 事件层——事件触发时参数可能尚未解析完整，只有 `execute` 的 params 才可靠。

> **命令超时：模型声明的 `timeout` 优先，策略值是天花板**（2026-10-11 修正）。
> 原先门禁完全忽略模型传的 `timeout`（bash 工具参数），一律用策略里的固定值。
> 实测代价：模型每条命令都写 `timeout: 20`，门禁却按策略跑 300 秒；一次全盘递归 grep 先占满 300 秒，
> 下一条卡住的命令又吃掉剩余预算，10 分钟的任务超时被耗尽，任务以「执行超时（600000ms）」失败 —— 用户看到机器人哑掉十分钟。
> 现在 `timeout: 3` 就 3 秒掐掉，并在返回里提示"若是全盘扫描请缩小范围"，模型能当场改小重试。
> 另外：门禁在收到 `SIGTERM`（外层任务超时杀 pi）时会**顺手 SIGKILL 正在跑的子进程**，
> 否则 `sh -c grep ...` 这类孙进程会变孤儿继续啃磁盘。

> **黑名单片段按「词边界」匹配，不是裸子串**（2026-10-11 修正）。裸子串会误伤：
> `commandDeny: ["rm "]` 会命中 `cd /Users/.../platform && node x.mjs` 里的 `platfo|rm |`，
> 于是该员工在项目目录下执行任何命令都被判"包含被禁止的片段"（实测真发生了，一次任务里 4 条命令全被拦）。
> 现在要求片段两侧是非单词字符或字符串边界：`"rm "` 仍命中 `rm -rf /tmp`、`; rm x`，但不再命中 `platform `/`form `。
> `-` 与 `_` 算单词字符；片段里的正则元字符会被转义（策略里本来就有 `:(){` 这种 fork-bomb 片段，当正则用会直接抛异常）。

### 4. 会话（Session）：员工 1:N

一个员工拥有**多个会话**，而不是绑死单会话（对齐 Pie 的 profile:session 一对多）：

| 属性 | 说明 |
|------|------|
| `sessionId` | 平台侧会话 id；`default` 为默认会话，映射到 pi 的 `waker-<id>`（向后兼容） |
| `name` | 可命名，默认按来源与首句自动生成（如 `飞书私聊`、`定时·周报 10-10 15:00`） |
| `externalKey` | 外部渠道会话 key（如 `feishu:u_<open_id>`），保证"同一个外部会话稳定落在同一个平台会话" |
| `source` | `cli` / `web` / `cron` / `im` / `api` |

行为约定：

- `waker chat` / `waker say` 默认走**默认会话**，退出再进仍是同一个人、记得聊过什么；加 `--new` / `--session <sid>` 可新开或指定；
- 多次 `waker say` 共享同一上下文，可跨进程调用；
- `waker run` 不进会话，每次独立（适合批处理）；
- 定时任务**每次执行新开一个会话**，不冲乱默认会话的上下文（见 §8.3）；
- 会话可重命名、**可清空**、可删除；存储于 `data/sessions.json`，上下文仍由 pi 原生会话文件持有。
- **默认会话只能清空、不能删除**：它是兜底会话（`resolveSession` 找不到指定会话时回落到它，`waker say`/`chat` 不带参数、按外部 key 建会话都以它为基准），删掉之后下一次任何"不指定会话"的调用都会把它重新建出来，用户看到的就是"删了又回来"。
- **清空** = 把该会话的 pi 会话文件**改名归档**（`*.jsonl.cleared-<时间戳>`）+ 消息计数归零。会话条目保留——会话 key、外部映射、命名都不该因为"想重置上下文"而丢失；改名而非删除，仍可人工翻回。
- 会话列表每行的**摘要取自 pi 会话文件的尾部**（会话内容的真源），不用任务流水：否则清空之后列表里还留着上一轮的问答，看着像仍有上下文、点进去却是空的。任务流水仍完整保留在 `data/tasks.jsonl` 里供回溯，只是不再当摘要用。

**并发规则**：冲突的单位是**一个 pi 会话文件**，所以串行按会话粒度——同一会话严格串行（排队而非拒绝），
同一员工的不同会话照常并行；另加每员工 3、全局 6 的并发上限，超出显示为「排队中」。
跨进程（CLI 与看板共用同一会话）由**文件锁**兜底，锁随持锁进程崩溃自动清理（详见 §4.4 运行时）。

### 5. 任务编目（Board / Task Ledger）

所有执行以**纯文本 JSONL** 编目（`data/tasks.jsonl`），可 grep、可 diff、可回溯。任务状态机：

```
arrived → queued → running → success / failed / cancelled
                          ↘ awaiting（待人工确认）
```

### 5.1 待办（Todos）

「任务编目」记**已经发生的执行**（不可变账本）；「待办」记**尚未发生的意图**（会改状态、会被顺延）。
两者分开存：`data/todos.jsonl`。放在一起会让"回溯"与"待办"互相污染——清空会话后流水还在，正是这个道理。

**人类任务与 agent 任务是同一种对象**，只差 `assignee`：

| assignee | 到点行为 |
|---|---|
| `human` | 看板上提醒人处理（不拉起 pi） |
| `agent` | 到点自动执行：沿用留下任务时的会话（上下文不断），结果回发到原窗口 |

**状态只在库里存三种终态**：`pending` / `done`（做完了）/ `dismissed`（不做了）。
`running` 只出现在 agent 执行期间。**到期与过期不入库**，由 `dueAt` 与当前时间派生
（`todoPhase()`，默认提前 24 小时算"到期"）——这样不需要后台扫库改状态，
看板关掉再打开也不会看到过期数据停在旧值。

看板表现（`web/src/components/TodoPanel.tsx`）：

- 到期：橙黄渐变**呼吸**（2.4s），只染卡片；
- 过期：红色脉冲（1.6s）+ 左侧色条；
- 点开卡片才出现「结束 / 关闭 / +1 天」，避免误触；
- 系统开启「减少动态效果」时降级为静态底色 + 色条，不闪烁。

agent 侧通过 pi 扩展 `extensions/todo.ts` 使用：`todo_add` / `todo_list` / `todo_done` / `todo_snooze`。
工具**直接调看板 HTTP**，不经 bash——`waker-guard` 的命令前缀白名单里没有 `waker`，
走命令行一定会被拦（实测如此，agent 当时只能去写 `待办.md` 并口头承诺）。
工具描述里写死了强制条款：**没拿到成功返回，不许回复"已记录"**。

接口：`GET/POST /api/todos`、`POST /api/todos/:id/{done,dismiss,snooze}`；`GET /api/board` 一并返回 `todos`。

## 四、功能说明

### 4.1 员工管理

| 能力 | 命令 / 入口 |
|------|-------------|
| 列出员工 | `waker agent list` / 看板左侧栏 |
| 查看档案与诊断 | `waker agent inspect <id>` |
| 新建员工 | `waker agent new <id> [--role "职责"] [--cwd 目录]` / 看板"新建员工" |
| 导入本机 agent | `waker import [<id>] [--cwd 目录]` / 看板"导入本机 agent"（不带 id 只列清单） |
| 平台开关 | `waker config [piAgents on\|off]`（是否自动纳管 Pi 侧 agent，默认 off） |
| 会话瘦身 | `waker compact <id> [--session <sid>] [--force] [--status]` / `POST /api/agents/:id/compact` |
| 常驻防睡眠 | 看板「工具 → 系统」开关 / `waker power [on\|off\|status]` |
| 编译身份与策略 | `waker compile <id>` |
| 编辑档案 | 看板"编辑档案"弹窗（基本信息含**工作目录** + SOUL / identity / persona / bible / MEMORY） |
| 删除员工 | 看板卡片「···」→ 删除（仅本地档案；纳管自 Pi 的不出现此项） |

**工作目录（cwd）**：编辑弹窗里可直接改（2026-10-11 补，此前只读、要手改 YAML）。两条硬校验：
**必须是绝对路径**、**目录必须已存在**（写进 YAML 之前就挡住错字）。
它同时是三件事，改动要当心：

1. pi 子进程的 spawn 目录；
2. guard 的文件系统边界（`policy.pathAllow` 通常以它为基准 —— 换了目录要同步检查白名单）；
3. **pi 会话目录的来源** —— pi 按 cwd 生成 slug 目录（`--Users-you-project--`），
   换 cwd 等于换了一个会话仓库：历史会话**不会丢**，但该员工的会话列表会变短。
   所以保存后后端会带回一条提醒，界面必须把它显示出来（否则又会被理解成"记录没了"）。

**删除的语义**（对齐"删除"这个承诺，四件事一起做）：

1. 把 `agents/<id>/` **移动**到 `data/archived/<id>-<时间戳>/` —— 是移动不是抹掉，随时能搬回来；
2. 清掉它的编译产物、渠道配置（含密钥）、头像；
3. 摘掉 `data/sessions.json` 里它的会话条目（否则留下孤儿会话；pi 原生会话文件不越界删除）；
4. **保留任务流水** —— 流水是不可变账本，删员工不该抹掉已发生的事实。

> 早先这里只删了编译产物、档案目录原封不动，于是 `loadAllWakers()` 下次照样扫到它，
> 用户点完删除发现"什么都没发生"。现在删除会立刻从列表消失。

### 4.2 对话与执行

| 能力 | 命令 | 说明 |
|------|------|------|
| 交互式对话 | `waker chat <id> [--new\|--session <sid>]` | 接管终端，保留会话 |
| 单句对话 | `waker say <id> "<msg>" [--session <sid>]` | 保留上下文，适合脚本 |
| 会话管理 | `waker sessions <id>` | 列出该员工的全部会话 |
| 清空 / 删除会话 | `waker sessions <id> --clear <sid>` / `--delete <sid>` | 清空保留会话；默认会话不可删 |
| 独立任务 | `waker run <id> "<prompt>"` | 不进会话，无上下文 |
| 看板内对话 | 看板气泡图标 → `POST /api/talk` | 与 CLI 共用同一条会话 |
| 记忆运维 | `waker memory review` / `rm <id>` | 挑出可疑记忆、按 id 删除（见 §4.9） |

### 4.3 调度

| 能力 | 命令 |
|------|------|
| 注册定时任务 | `waker cron add <id> "<cron>" "<prompt>"` |
| 启动调度器 | `waker board`（随看板启动，注册 cron + 一次性任务） |

### 4.4 看板（Web）

启动：`waker board --port 8787` → 打开 `http://127.0.0.1:8787`

看板提供：

- **顶栏（TopBar）**：品牌标识、全局搜索、**依赖健康灯（Pi / 记忆服务）**、渠道灯、工具入口、手动刷新；
- **总览栏（OverviewBar）**：任务维度——运行中 / 待确认 / 失败 / 成功、今日任务、员工数、数据心跳；
- **员工栏（WakerRail）**：全部员工、岗位、今日任务数、运行中数量；单卡可对话 / 编辑；
- **任务板（TaskBoard）**：按状态（全部 / 运行中 / 待确认 / 失败 / 成功）与来源（手动 / 定时 / IM / API / 看板）筛选；列表高度**按视口实测**（不写死），大屏用满、小屏保底，不会把下面的面板挤走；
- **运行时（RuntimePanel）**：有执行时才出现——列出此刻在跑的 pi 子进程（员工、来源、pid、已运行时长）与**实时输出尾部**，可逐个终止。

> 运行时只覆盖**看板进程自己拉起**的执行。CLI（`waker say` / `run`）是独立进程，其运行态不在登记表内。

#### 编辑档案 · 权限页签（2026-10-14 补）

员工的权限原来只能手改 `agents/<id>/waker.yaml`，改完还得记得重编译。现在看板「编辑档案」里多了一个
**权限**页签，直接编辑生效值：

- **可读写目录**（`policy.pathAllow`）：路径清单，单条增删（不用逗号分隔——路径里出现空格、逗号都不奇怪），
  一键「加上工作目录」；为空时界面明说**等于不限制**；
- **保护名单**（`policy.pathDeny`）：写片段即可（`.ssh` / `.env`），read 与 bash 都管；清空时提醒"凭据不再被拦"；
- **允许它修改自己的档案**（`policy.selfEdit`）：见 §7.2。

三处实现要点：

1. **写回用 yaml 的 Document API 原地改键**（`parseDocument` + `setIn` + `toString`），保留文件里的注释与排版；
   用 `parse` + `stringify` 会把整个 `waker.yaml` 重排，注释全丢。
2. **写完立即重编译**（`writeCompiledArtifacts`）——guard 读的是 `data/policy/<id>.policy.json`，
   不重编译就是"界面上改了、门禁还是老规则"，比不能改更糟。
3. **只提交真的变了的字段**：`pathAllow` 有"空 = 不限制"的语义，每次全量回传会把"没配"变成"显式配成空"，
   等效但会把文件越改越脏。

保存后后端会回**副作用提醒**（不是形如"保存成功"的废话）：白名单不含它自己的工作目录、白名单里有不存在的目录、
把白名单清空、把保护名单清空、开启/关闭自改——这些都必须让人看见。

#### Markdown 渲染（2026-10-11 补）

员工的产出**大量用 Markdown 组织信息**（`**加粗**` / `## 标题` / `- 列表` / 表格 / 围栏代码块）。
之前一律按纯文本显示，读者看到的是一堆源码符号——回复质量看着像"没写完"。

- **看板**：`web/src/components/Md.tsx` 统一渲染（`react-markdown` + `remark-gfm`），
  接在**聊天气泡（员工回复侧）**与**任务详情「最终产出」**上；用户自己发的那条不渲染
  （聊天框里随手敲的 `1.`、`*` 会被当结构改写）。代码块与表格横向可滚，宽表不会撑破气泡。
- **安全**：不启用 `rehype-raw`，模型输出里的原始 HTML 一律当文本；链接统一
  `target=_blank rel=noreferrer`，`javascript:` 之类由 `react-markdown` 默认的 `urlTransform` 拦掉。
- **为什么不用 `@tailwindcss/typography`**：它的间距按 16px 正文设计，塞进 13px 的聊天气泡会松垮，
  `Md` 按气泡尺度手写样式并对齐全局 token。

#### 工具 → 系统：常驻防睡眠（2026-10-20 补）

原来只有"任务运行期间"的防睡眠（随每个 pi 子进程起落的临时断言）。它解决不了另一种情况：
**没有任务在跑、但机器该醒着**（等 IM 消息、等定时任务、机器上还跑着别的东西）。

所以工具弹窗多了「系统」页，一个开关：

| | 说明 |
|---|---|
| 实现 | `caffeinate -i -s -w <看板 pid>`，一条**长驻**电源断言（`-i` 防空闲睡眠、`-s` 防系统睡眠；不加 `-d`，屏幕该黑就黑） |
| 绑定 | 绑**看板进程的 pid**：看板退出/崩溃 → 断言自动消失，不留孤儿；重启按配置自动恢复 |
| 持久化 | `data/config.json` 的 `preventSleep`；接口 `GET/POST /api/power` |
| 命令行 | `waker power [on\|off\|status]`。CLI **只通过 HTTP 改看板**——自己起断言会随 CLI 退出立刻失效 |
| 状态 | `{supported, enabled, active, pid, since, note}`：`enabled` 是开关、`active` 是断言真的在跑，两者不一致时界面把原因说出来 |

两个实现细节值得记：

1. **必须 `unref()`**：断言绑的是本进程 pid，不 unref 的话 Node 会等子进程退出才肯退出，
   而子进程只在父进程死后才退——直接把进程锁死。
2. **不支持时不假装成功**：非 macOS / 找不到 `caffeinate` / `WAKER_NO_CAFFEINATE=1` 时，
   开关照样记下来（换台机器就生效），但 `active=false` 且 `note` 说明原因，界面禁用开关并显示那句话。

实测（`pmset -g assertions`）：

```
pid 98013(caffeinate): PreventUserIdleSystemSleep  named: "caffeinate command-line tool"
        Details: caffeinate asserting on behalf of Process ID 97108   ← 看板进程
pid 98013(caffeinate): PreventSystemSleep          named: "caffeinate command-line tool"
```

重启看板后断言按配置重建、重新绑到新 pid；关掉后 `pmset` 里立刻消失。

### 4.5 通道接入（IM）：可插拔 Channel 层

渠道已抽象为平台对象（对齐 Pie 的 Channels 层），**随看板进程一起启动，不需要独立的 bot 进程**：

```
外部消息 → Channel（协议翻译）→ 会话 key → 平台会话 → runner 执行 → 回帖
```

| 能力 | 说明 |
|------|------|
| 抽象 | `Channel` 接口（入站 / 出站 / 状态）+ `ChannelManager`；目前实现 `feishu`，预留微信 / Discord / 钉钉 |
| 配置 | 每个员工**一套自己的飞书应用**：`waker.yaml` 的 `channels.feishu`（`enabled` / `appId`），密钥放同目录 `secrets.json`（已 gitignore） |
| 入站 | `im.message.receive_v1` **长连接**（无需公网与回调地址）；会话 key 形如 `u_<open_id>` / `g_<chat_id>` |
| 会话映射 | 会话 key ↔ 平台会话一一对应，同一个外部会话稳定落在同一个平台会话 |
| 出站 | 结果回帖到原外部会话；**Markdown 按交互卡片渲染**（见下）；agent 主动发消息仍复用 Pi 扩展的 `feishu_*` 工具 |
| 出站渲染 | 有 Markdown 记号（`**` / `##` / 列表 / 表格 / 围栏）时发 `msg_type=interactive` 卡片，否则保持纯文本短消息。`src/channels/mdCard.ts` 做转换，**卡片发不出去自动回落纯文本**——渲染是加分项，答案丢失不是 |
| 出站渲染的降级 | 卡片**只支持 `markdown` / `hr` 这几个元素**：代码块必须留在 markdown 元素里用围栏语法（实测独立 `code` 元素被接口拒收：`not support tag: code`）；`#` 标题降级为加粗；表格转成「字段: 值」列表。超长内容按**元素边界**分包，不从句子中间切断 |
| 收到反馈 | 收到消息**先给原消息加个表情**（默认 👍 `THUMBSUP`，可用 `channels.feishu.ackEmoji` 换），再回正文——执行动辄几十秒，没有这一步用户不知道"到底收到没有"。忙锁排队时同样先加。表情只能加在**用户发的消息**上（对机器人自己的消息调用返回 `231017`），**文档评论没有表情能力**，那边只能靠"还在处理中"的回帖 |
| 会话命令 | 在 IM 里直接发 `/clear`（或 `清空` / `清空上下文` / `/reset`）→ **不进模型**，直接清空**当前外部会话**的上下文并回执；`/help` 列出命令。只认精确匹配，所以"帮我清空这段文字"不会被误判。只作用于该飞书会话，不动默认会话与别的群 |
| 文档评论 | `drive.notice.comment_add_v1`：云文档里 @ 机器人也能触发（事件不含正文，需再查一次评论）；回复走**评论回复接口** |
| 评论回复兜底 | 评论回复被飞书拒绝时按序退让：① **新开一条评论并 @ 提问者**（实测该路径可用）② **私聊**。否则答案只留在日志里，用户看到的是"@ 了没反应" |
| 可观测 | `GET /api/channels` 暴露状态，看板顶栏显示渠道灯；`waker channels` 列出各员工渠道配置 |
| 幂等去重 | **两道闸门**（2026-10-12 补第二道）：① 事件自带时间戳比现在早 **10 分钟以上**直接丢弃——与状态无关，能挡住任何"晚到重投"；② 事件 id（`message_id` / `comment_id`）去重，**落盘 `data/feishu-seen.json`**、窗口 24 小时、跨进程重启存活 |
| ack 时机 | 飞书要求收到事件后回 ack，而 SDK 是**等 handler 全部 await 完**才回（`[ws] receive message` 分支：先 invoke、再 sendMessage）——所以 handler **必须立刻返回、不能在 handler 里 await 任务**。否则 ack 迟到，飞书按自己的重试计划重投：**实测两档间隔 +18~19 秒、+1 小时 4 秒**（用户 01:06:31 / 01:07:37 的提问，在 02:06:35 / 02:07:41 被原样重跑）。重投是否变成"答两遍"，取决于第一次任务有没有在那个间隔内跑完——短问题更容易中招 |

```yaml
# agents/<id>/waker.yaml
channels:
  feishu:
    enabled: true
    appId: cli_xxxxxxxx
```

#### 会话如何分配

| 来源 | 会话键 | 粒度 | 说明 |
|------|--------|------|------|
| 私聊 | `feishu:u_<open_id>` | **每个用户**一个会话 | 名「飞书私聊」 |
| 群聊 | `feishu:g_<chat_id>` | **每个群**一个会话 | 名「飞书群聊」；群里所有人**共用一段上下文** |
| 云文档评论 | `feishu:doc_<file_token>` | **每篇文档**一个会话 | 名「飞书文档评论 docx」；按文档而非按人 |
| 多维表评论 | `feishu:doc_<file_token>` | 每张表一个会话 | 走同一事件（`file_type: bitable`），**未实测** |

同一个键永远落在同一个平台会话，所以"同一个飞书会话"始终是同一人格、同一段上下文。

#### 三条硬约束

1. **一个飞书应用只能由一个员工接入。** 平台会检测 `appId` 重复：先配齐凭证的那个占用名额，
   其余在启动时被拒绝并把原因写进渠道状态（看板渠道灯 / `waker channels` 都能看到）。
   —— 飞书一个应用只该有一条长连接收事件，多开会互相争抢：要么都回造成重复，要么随机一方回造成"谁答不确定"。
   多员工各自独立 → **各自建一个飞书应用**。
2. **旧的独立 `feishu-bot` 必须停掉**（`launchctl bootout gui/$(id -u)/dev.pi.feishu-bot` + `launchctl disable gui/$(id -u)/dev.pi.feishu-bot`）。
   它连的是同一个 appId，与平台渠道直接抢事件；它回的消息也**不进平台会话流水**，看板上看不到。
   ⚠️ **但不要删 `~/.pi/agent/feishu-bot/` 这个目录**：waker 的飞书渠道复用其中已安装的
   `@larksuiteoapi/node-sdk`（`channels/feishu.ts` 按它的 `package.json` 解析依赖），删了渠道就起不来。
   只需停服务，文件留着。
3. **群里"不用 @ 就处理每条消息"需要两件事同时成立**：
   - 飞书侧：为应用开通「获取群组中所有消息」权限（默认只有「接收群聊中@机器人消息事件」，
     不开通的话飞书**根本不会把非 @ 消息推过来**）；
   - 平台侧：`allowAllChats: true`（或把群 `chat_id` 加进 `allowedChats`）。

   平台代码本身**不检查是否 @ 了机器人**：只要能收到、且白名单放行，就会处理。
   代价是群里每条文本都会触发一次执行（消耗与刷屏风险），建议用 `allowedChats` 精确加白。

### 4.7 Pi 资产：导入本机 agent（不再自动纳管）

Waker 能读取本机 Pi 生态里既有的 agent / subagent（`~/.pi/agent/agents/*.md`：单 Markdown 文件 + YAML frontmatter），
有**两条路**，都不需要你在平台内重建员工：

| 方式 | 命令 / 入口 | 结果 |
|------|------------|------|
| **导入**（推荐） | `waker import <id>` / 看板左侧「导入本机 agent」 | 在 `agents/<id>/` 生成**完整平台档案**，彻底收编 |
| 自动纳管（默认**关**） | `waker config piAgents on` | Pi 侧**全部** profile 以只读形式直接出现在名册里 |

**为什么默认不自动纳管**（2026-10-11 调整）：纳管出来的员工只读——名称 / 岗位 / 模型由 frontmatter 决定、
策略段装不下（命令白名单为空）、平台还不能归档——把它们全部混进名册，实用性低于"按需收编一个"。
`waker import` 不带 id 时只列清单（标注"可导入 / 已导入"），不会批量导入。

#### 导入：把一个 Pi agent 收编成平台档案

```bash
waker import                  # 列出本机 Pi agent 及状态
waker import coder            # 导入（可加 --cwd 指定工作目录）
```

导入做四件事：

1. 在 `agents/<id>/` 生成**五件套**（SOUL / identity / persona / bible / MEMORY）；
2. frontmatter 映射为平台字段：`description`→`role`、`display_name`→`name`、`model`→`model`、`tools`→`policy.toolAllow`；
3. **正文整体进 `SOUL.md`**，不自动拆分 —— 拆"我是谁 / 工作风格 / 红线"要读懂内容，机器硬拆只会拆错；
   identity / persona / bible 是占位，由人按需搬段落（**搬完要从 SOUL 删掉**，两处都写会重复注入）；
4. 立即编译（否则首次对话扩展读不到策略会 fail-open）。

导入后的性质：

- **零分叉**：Pi 侧文件原样保留（不删、不改）；同名时本地档案优先，那份自动隐去。想回退就归档（或删掉目录），Pi 版立刻回来；
- **能改能删**：可以改名称 / 岗位 / 模型 / 策略，也可以归档，与新建的员工完全等价；
- **渠道不受影响**：渠道配置按员工 id 存在 `data/channels/<id>.json`，与档案目录解耦；
- **不替你收紧命令**：导入只复刻 `tools`，**命令白名单仍为空**（与 Pi 侧一致）——随手写白名单会把它的能力废掉。
  确认过工作流需要哪些命令后，再在 `waker.yaml` 里加 `policy.commandAllow`（模板注释里有示例）；
- **别设过窄的 `pathAllow`**：若它的 skill 库在 `~/.pi/agent/skills/`，路径白名单过窄会直接废掉工作流（读不到必读件）；
- **记忆不跟随**：记忆按 `WAKER_ID` 隔离，新档案的私有命名空间是空的。需要的话用"复制记忆"补（见 §9），或靠共享档 + 自然积累。

> 手工接管（不跑 `waker import`，自己写档案）仍然可行，适合需要**按功能拆分**正文的场景——
> 平台的 `Public-Opinion` 就是这么接管的：正文拆成「调性/判断倾向」「我读什么文件、按什么流程写」，
> 分别进 SOUL 与 persona。但要记得同步 `waker compile <id>`。

#### 自动纳管模式下的只读边界（若你把它打开）

- 扫描 `~/.pi/agent/agents/*.md`，解析 `description` / `display_name` / `model` / `tools` / `enabled`；
- profile 正文 → 人设总纲（frontmatter 剥离，不进提示词）；`model` / `tools` → 运行参数；
- 看板中以 **`Pi` 徽标**区分来源，与本地档案（`local`）并列展示；
- **半开放纳管**（原来写成"只读"，不准确，2026-10-11 修正）：
  - **人设正文可编辑**：平台只替换 profile 的正文，frontmatter 原样保留；
  - **基本信息不可改**：名称 / 岗位 / 模型由 frontmatter 决定，编辑入口隐藏；
  - **没有策略段**：工具集取 `tools`，而**命令白名单为空（除黑名单外皆可执行）**；
  - **不可归档**：平台不代为删除 Pi 侧文件。

同名冲突时**本地档案优先**。开关是平台级的：`data/config.json` 的 `piAgents`（默认 false），也可用环境变量
`WAKER_PI_AGENTS=on|off` 临时覆盖。

### 4.8 会话自动瘦身（长上下文压缩）

对话是长跑的，pi 的会话文件只增不减：实测一条飞书私聊涨到 **147KB（≈4 万 token）**，之后
**每条新消息都把它整段带上** —— 又贵，又容易把旧话题带进新问题。

**做法：交给 pi 原生 compaction，平台只观察与手动触发（2026-10-11 改）**

pi 自己就有这套机制，且**默认开启**（`DEFAULT_COMPACTION_SETTINGS = { enabled: true, reserveTokens: 16384, keepRecentTokens: 20000 }`）：
压缩时在**同一个** JSONL 里插一条 `type: "compaction"` 记录（`summary` 就是压缩内容），
**之前的记录一条不删**；装配上下文时用 `getLatestCompactionEntry()` 定位边界，**从压缩处之后开始加载**。

> **为什么改（这是一次真实事故）**：平台原先自己实现压缩 —— 摘要 → `clearSession` 把会话文件
> **改名归档** → 用同一个 `--session-id` 把纪要"种回"一个新会话。结果是**用户的对话记录整段消失**
> （界面上 199KB 历史只剩两条"上下文备忘"）。用户的原话是
> 「可以瘦身，但不能改我的对话记录，否则我脑子里的记忆也会消失；可以在对话记录中间加个压缩后的内容，
> 下一轮加载 history 时从压缩内容刚开始加载」—— 而这正是 pi 原生的语义，白绕一圈反而做错了。
> 原先"pi 驱动不了压缩"的判断也是错的：扩展 API 有 `ctx.compact()`，还有 `session_compact` 事件。

平台现在只做三件**不碰会话文件**的事：

| 职责 | 落点 | 说明 |
|------|------|------|
| 观测 | `core/compact.ts` 的 `maybeCompact` | 任务结束后只算 token、超告警线时打一条日志 |
| 手动触发 | `waker compact <id> --force` / `POST /api/agents/:id/compact` | 带 `WAKER_FORCE_COMPACT` 跑一次轻量 run，由 `extensions/waker-compact.ts` 调 `ctx.compact()` |
| 留痕 | `data/context/<id>/compactions.jsonl` | 每次压缩记一行：token 数、触发原因（manual/threshold/overflow）、摘要 |

强制压缩完成后，摘要是**从会话记录本身读回来**的（compaction 节点的 `summary`），另存一份
`data/context/<id>/<session>-<时间戳>.md` 供人工核对。若 pi 判定"还没到需要压缩的程度"，命令会**如实说明**
（报当前 token 与 pi 的保留窗口），不会假装失败。

**token 口径必须跟 pi 一致**（这也是事故的第二个原因）：旧实现按 `字节 / 3.5` 估，把 JSON 包裹、
工具输出、thinking 段全算进去，把一个真实 28,070 token 的会话报成 **56,920**，于是误触发了那次破坏性压缩。
现在 `sessionSize()` 优先取最后一条 assistant 消息的 `usage.totalTokens`（pi 自己就是这么算的），
拿不到才退回"文本字符数 / 4"。**宁可低估也不要虚高**——虚高会让人以为该压缩了。

> 界面上看不到压缩这件事曾被当成"记录丢了"。现在聊天窗会显示压缩节点的留痕，
> 且任何情况下**平台都不会改名、移动、删除用户的会话文件**。

```jsonc
// data/config.json
{ "context": { "enabled": true, "maxTokens": 30000, "keepTokens": 6000 } }
```

- `maxTokens` 触发阈值（估算 token，≈字节/3.5），下限 1000；
- `keepTokens` 压缩目标，同时作为纪要字数上限，下限 200；
- 关掉 `enabled` 就永不自动压（手动命令仍可用）。

手动入口：`waker compact <id> [--session <sid>] [--force] [--status]`，
或 `POST /api/agents/:id/compact`（body 可带 `sessionId` / `force`）。
纪要落盘在 `data/context/<员工>/<会话>-<时间戳>.md`，供人工核对；日志里也会打一行 `[compact] 已瘦身 …`。

> 实测（`chat` 的临时会话）：4654 token → 纪要 305 字，新会话文件 ~940 token，
> 压缩后追问"我让你记的词是什么"仍能正确答出（上下文接得上）。

### 4.9 per-profile 配置：模型与凭证

每个员工有**自己的一套** LLM 与渠道凭证，而不是全局共用一套：

- **LLM**：`waker.yaml` 的 `llm` 段（`provider` / `model` / `thinking`），`apiKey` 放同目录 `secrets.json`;
- **渠道**：`channels.feishu`（`enabled` / `appId`），`appSecret` 同样放 `secrets.json`;
- 合并优先级：`secrets.json` > `waker.yaml`；密钥文件已 gitignore（`agents/*/secrets.json`）;
- 运行期由 `llmArgs()` 映射为 pi 的 `--provider` / `--model` / `--api-key` / `--thinking`;
- `waker agent inspect` 脱敏展示，只暴露 `hasApiKey` / `hasAppSecret`，不返回明文。

```yaml
# agents/<id>/waker.yaml
llm:
  provider: deepseek
  model: deepseek-v4-pro
  thinking: medium
```

```json
// agents/<id>/secrets.json （已 gitignore）
{ "llm": { "apiKey": "sk-..." }, "feishu": { "appSecret": "..." } }
```

### 4.9 记忆运维

记忆一旦入库就会被**反复注入**后续会话，所以库里不该有的东西是长期成本。策略是"源头约束 + 人工审阅"，
**不做自动 TTL**（误删长期记忆的代价远大于多留几条垃圾）：

| 环节 | 做法 |
|------|------|
| 写入 | 抽取侧明确禁止记**进行中的临时状态**（"正在调试 X"）、一次性反馈、碎片口令；要抽就抽背后稳定的那部分 |
| 审阅 | `waker memory review [--ns <ns>] [--all]`：按高置信规则挑出可疑条目（碎片口令 / 短句进行时 / 完全重复），人工决定 |
| 删除 | `waker memory rm <id>...`；批量 `waker memory rm --transient --yes` |
| 搬运 | 旧单例 pi-memory（`:8970`，留给 pi-web）的记忆按需增量搬入，见 `vendor/multi-pi-memory/README.md` |

## 七、安全模型

| 层 | 机制 |
|----|------|
| 命令 | 前缀白名单 + 片段黑名单 + 高危人工确认 |
| 路径 | 目录白名单（`pathAllow`）+ 凭据路径保护（`pathDeny`） |
| 执行 | 可选 Docker 容器，无外网、随容器销毁 |
| 拦截反馈 | 被拦截时模型收到明确原因，并被要求**不换写法绕过** |

策略段示例（`waker.yaml`）：

```yaml
policy:
  sandbox: false
  commandAllow: ["ls", "cat", "grep", "find", "git"]
  commandDeny: ["rm ", "curl", "sudo", "chmod"]
  pathAllow: ["/your/workdir"]
  pathDeny: [".ssh", ".aws", ".env"]
  requireConfirm: ["删除文件", "推送到远程", "发布"]
```

### 7.1 路径范围到底管住了什么（2026-10-14 修正）

**配置在哪**：`agents/<id>/waker.yaml` 的 `policy.pathAllow`（目录白名单，最长前缀匹配；**留空 = 路径不设限**）。
看板「编辑档案 → 基本信息」里的**工作目录（cwd）**是另一件事——它是 pi 子进程的启动目录、也是 **pi 会话目录的来源**，新建员工的模板会顺手把 `pathAllow` 设成 `[cwd]`，所以两者**常被当成一回事，其实不是**。

**实际生效范围（逐工具，已实测）**：

| 工具 | 是否受 `pathAllow` 约束 | 是否受 `pathDeny` 约束 |
|---|---|---|
| `read` / `write` / `edit` | ✅ | ✅ |
| `ls` / `grep` / `find` | ✅（2026-10-14 补：它们同样是读路径入口，只拦 read 等于把读取范围交给它们穿透） | ✅ |
| `bash` | ❌ **不检查路径**，只受命令白/黑名单与 `pathDeny` 的凭据片段约束 | 部分（凭据片段） |

> **bash 这个口子是真的**：实测 `cat /etc/hosts` 在 `pathAllow: [~/Documents]` 下照样执行得通
> （命令白名单里 `cat` 是放行的）。命令层拦的是"危险动作"（`rm` / `curl` / `sudo` …），
> 不是"危险位置"。要连位置一起管，只能开 `sandbox: true` 走容器，或把 `commandAllow` 收到极窄。
> 这一点写明白，比让人以为"设了 pathAllow 就万无一失"要好。

**一个曾经静默失效的坑**（值得记住，因为它教过一次"看着有校验其实没有"）：
guard 读工具参数用的是 `event.args`，而 pi 0.84 起的字段名是 **`event.input`** →
永远取到 undefined → 路径判定里的目标退化成 cwd（`resolve(cwd, '')`）→
**而 cwd 通常在 `pathAllow` 之内 → 白名单静默失效**：`read /etc/hosts` 一路放行、`blockedCount` 还是 0。
现在两个字段都认，且 `ls/grep/find` 一并纳入；`types/pi-shim.d.ts` 也补了 `input`，
避免"类型检查通过、运行时字段名不对"这类问题再被掩盖。

实测（临时员工 `pathAllow: [~/Documents]`）：

```
ls   ~/work      → 拦截：目标路径越出该岗位的可读写目录
grep localhost /etc              → 拦截
find README.md ~/...  → 拦截
read /etc/hosts                  → 拦截
ls   ~/Documents       → 成功（范围内，无误伤）
```

### 7.2 员工改自己的档案：能改自己，不能改权限（2026-10-14）

需求原话是"我需要让 worker 修改自己的 prompt"。**光把写权限放开是不行的**，那等于给它一把没有痕迹的钥匙。
所以做成一个默认关闭的开关 + 一条受控通道：

```yaml
policy:
  selfEdit: true      # 开启后它拿到 waker_self_edit 工具
```

它只能改这五份文本：`SOUL.md` / `identity.md` / `persona.md` / `bible.md` / `MEMORY.md`。
三条硬约束都不依赖它自觉：

| 约束 | 落点 |
|---|---|
| **改不了权限** | `waker.yaml` 不在白名单；工具按**文件名硬拒**（不是靠内容判断），说"我换个写法"也绕不过 |
| **写前强制备份** | 旧内容 → `data/identity-history/<id>/<文件>.<时间戳>.bak` |
| **每次留痕** | 追加一行 → `data/selfedit.jsonl`（含它写的 `reason` 与前后字节数） |

**回滚通道**（没有它，备份就只是"写了不读"的摆设）：

```bash
waker identity <id>                          # 开关状态、可回滚版本、最近留痕
waker identity <id> restore MEMORY.md [时间戳片段]   # 回滚（走平台正规写入口，写完重新编译）
```

**生效时机**：写回后不重新编译、也不去看板接口——外壳在每次 spawn pi 之前都会 `writeCompiledArtifacts(rec)`，
所以**下一个任务/下一轮对话**自然拿到新档案。好处是这个扩展**不依赖看板进程是否在跑**（CLI 直跑 `waker say` 也成立）。

两个真实踩到的坑（都值得记住）：

1. **`--tools` 是整体替换活跃工具集**。岗位配了 `policy.toolAllow` 时，runner 会传
   `--tools read,bash,...`，pi 的 `setActiveToolsByName` 只认这份名单里的名字——
   **扩展注册的自定义工具会被"注册了但模型看不见"**：开关开了、工具也注册成功，模型却完全不知道有它。
   现在 `selfEdit` 打开时会把 `waker_self_edit` 补进 `--tools`。
2. **guard 必须给这个工具开绿灯，且要排在工具白名单判定之前**。否则 `toolAllow` 里没有它，
   会被"不在白名单内"拦掉，开关形同虚设。

实测（临时员工，`selfEdit: true` + `pathAllow: [/tmp/...]`，全流程真跑）：

```
waker_self_edit list                 → 返回五份档案与备份目录
waker_self_edit write MEMORY.md      → 79→51 字节，旧版本已备份，已记入审计流水
waker_self_edit write waker.yaml     → 拒绝：只能操作那五份（改不了权限）
read /etc/hosts                      → 拦截（pathAllow 之外）；blockedCount=1
waker identity <id> restore MEMORY.md → 内容回到 79 字节原样
```

> 顺带印证了 §7.1 那条：`bash cat /etc/hosts` **仍然不被拦**（bash 只校验命令名，不校验参数里的路径）。
> 这不是本次引入的问题，也正因如此，"开了 selfEdit 就等于安全"是错的——它只解决"改自己"，不解决"越界读"。

### 7.3 浏览器能力：一条连接，多种前端（2026-10-25）

**为什么需要一个常驻 broker，而不是给每个 agent 各装一套**

`@browsermcp/mcp` 启动时会 `lsof -ti:9009 | xargs kill -9`，而 Chrome 扩展把地址写死成
`ws://localhost:9009`；同一个 server 也只保留一条扩展连接（新连接会顶掉旧的）。
revolver 每跑一个任务就新起一个 pi 进程——若各自 spawn，就会互相 kill、互相顶号，
表现为"第一次能用，第二次坏"。所以浏览器只由**一个**常驻 broker 持有：

```
Chrome + Browser MCP 扩展
        │ ws://localhost:9009（单连接）
        ▼
browser-broker（常驻，唯一持有一份 browsermcp 子进程）
  ├─ HTTP 127.0.0.1:8790  /status /tools /call   → pi 扩展（revolver 的 agent）
  └─ waker browser mcp-stdio（stdio↔HTTP 转接）   → CodeBuddy 等外部 MCP 客户端
```

**开启方式**

```bash
waker browser start --detach   # 起 broker（上游是懒启动：首次调用才 spawn）
waker browser status           # 上游 pid / 扩展连没连 / 队列水位 / 最近错误
# Chrome 里点 Browser MCP 扩展图标 → Connect（这一步只能人工做）
```

员工侧开关有两个入口（另可直接改 yaml），改的都是 `policy.browser`（默认关）：

- **名册卡片右侧的地球图标**：点一下即切（title 显示"已开（点击关闭）/ 已关（点击开启）"）；
- 「⋯」→「Agent 设置」→「能力与权限」→ 勾选「允许它操作浏览器」→ 保存权限；
- 或直接改 `agents/<id>/waker.yaml`：

```yaml
policy:
  browser: true
```

> 注意 `registry` 解析 `policy` 是**逐字段白名单**：只在类型里加字段、不加解析行，
> 会变成"界面上开了、yaml 里写了，但 guard 与 runner 永远看不到"（这次踩过一次）。

开启后该员工拿到**一个** `browser` 工具，参数是多行命令 DSL
（`goto` / `back` / `forward` / `reload` / `click` / `fill` / `type` / `press` / `select` /
`check` / `wait` / `tab list|new|select|close` / `snapshot` / `find` / `get` / `screenshot` /
`eval` / `scroll` / `hover` / `drag` / `upload` / `dialog` / `console` / `requests`），
一行一条、遇错即停，一次调用可以走完多步。
`runner` 会把工具名并进 `--tools`，`guard` 在工具白名单判定**之前**放行——
漏任一处都会变成"注册了但模型看不见"（`waker_self_edit` 踩过这个坑，见 §7.2）。

> 2026-11-08 对齐 `@browsermcp/mcp` 2.x：上游把 13 个原子工具合并成 `browser` 一个，
> 并把架构改成"扩展 → 常驻 daemon（`127.0.0.1:9010`）→ MCP 客户端"。还用 1.x 的
> 13 个名字注册时，`--tools` 里全是上游不认识的名字，调用一律回
> `Unknown tool browser_snapshot`——看起来像"扩展没连"，实际是版本契约对不上。
> 上游版本现已钉死（`DEFAULT_UPSTREAM_ARGS`），升级必须同步改 `browserTools.ts` 与这两个测试。

**通道语义（四条必须知道的）**

| 事实 | 后果 |
|---|---|
| 浏览器是**单标签页** | 调用在 broker 里串行；队列满（默认 8）直接拒绝，不无限堆积 |
| 操作不可逆 | 误点删除/发布真的会发生；建议同时保 `requireConfirm` 的"发布 / 对外发送" |
| 扩展连的是 daemon，不是 broker | 2.x 由 Chrome 侧常驻 `daemon.js`（9010）持有连接；broker 只是个串行化的调用方，重启 broker 不影响扩展 |
| 9009 已不再使用 | 1.x 那套"server 抢 9009、后起的杀掉先起的"不存在了；外部客户端一律走 `waker browser mcp-stdio` |

**CodeBuddy 侧的改法**（`~/.codebuddy/mcp.json`）：

```json
"browser": { "type": "stdio", "command": "/usr/local/bin/waker", "args": ["browser", "mcp-stdio"] }
```

桥只转发 HTTP；broker 没起时 `tools/call` 返回带提示的 `isError`，不会把客户端会话搞崩。

**诊断口径**（三者别混）：

- `浏览器桥不可达` → broker 没起，去 `waker browser start`；
- `No connection to browser extension` / `There's no tab yet` → 浏览器侧没连上：
  确认 Chrome 已打开、Browser MCP 扩展处于启用状态（2.x 不再需要点 Connect），
  `waker browser status` 会显示"未连接"；
- `Unknown tool browser_*` → **版本契约对不上**（上游被解析到 2.x 而登记的还是 1.x 名字），
  不是扩展问题；检查 `DEFAULT_UPSTREAM_ARGS` 的版本与 `browserTools.ts` 是否一致。

### 8.1 看板布局与交互

```
┌─ 顶栏：品牌 / 搜索 / 依赖健康 / 渠道 / 工具 / 刷新 ──────────────────┐
├─ 总览栏：运行中 · 待确认 · 失败 · 成功 · 今日任务 · 员工 · 心跳 ─────┤
│  ┌──────────┐   ┌──────────────────────────────────────────┐      │
│  │ 员工列表  │   │ 运行时（有执行时出现：进程 + 输出尾部 + 终止）│     │
│  │ （窄栏）  │   ├──────────────────┬───────────────────────┤      │
│  │ 头像+名字 │   │ 未读会话（全局）  │ 使用统计（热力图+tokens）│     │
│  │ 对话 ···  │   ├──────────────────┴───────────────────────┤      │
│  └──────────┘   │ 对话记录（会话粒度）        │ 定时任务      │      │
│                 └──────────────────────────────────────────┘      │
└──────────────────────────────────────────────────────────────────┘
```

- **左栏（员工）**：窄栏卡片（头像 + 名字 + 岗位 + 来源徽标）。卡片上有三个动作：**对话**、**地球图标**（浏览器能力开关，灰=关 / 主色=开）、**「···」菜单**（Agent 设置 / 删除）。纳管自 Pi 的员工不出现浏览器开关与"删除"项。
- **Agent 设置弹窗**（原「Agent 设置」+「飞书链接设置」+「浏览器开关」三个入口合并）：同一页分三块 ——
  **设置**（基本信息 / 能力与权限 / 飞书渠道）· **运行**（技能 / 头像）· **档案**（SOUL / identity / persona / bible / MEMORY）。
  飞书渠道保存后立即 `reloadChannels`，不用重启看板。
- **右侧工作区**：顶部为总览栏，其下是**使用统计**；下方左右分栏——**左 = 对话列表，右 = 定时任务列表**。
- **改 bot 名称**：「···」→ **Agent 设置 → 基本信息**，可改**名称 / 岗位 / 模型**（写回 `agents/<id>/waker.yaml`，**保留原注释与排版**）。纳管自 Pi 的 profile 只读，需到 Pi 侧修改。
- **健康探测**：对 docker / pi 的可用性探测为**异步 + 60 秒缓存**。此前用同步 `execFileSync` 探测，docker 未安装时每次都会卡满超时，把单线程事件循环堵死、殃及其它请求。
- **未读会话**：在使用统计左侧，集中列出"有新结果还没看"的会话（**全局视角**，不随左侧员工筛选变化）；点击即打开并自动标为已读，支持「全部已读」。与员工卡上的红点角标互为补充——角标说"谁有"，这里说"具体哪几条、最后说了什么"。
- **对话窗**：从**右侧滑出的侧栏**（不遮挡看板，看板仍可操作），打开即定位到最新消息，且**不做平滑滚动**。
  - 发送用 **⌘/Ctrl + Enter**，单独 Enter 换行（长指令是多行的，误发代价大）；
  - **点面板之外的任何地方即收起**，输入框里没发出去的草稿按「员工:会话」存在本地，重新打开自动还原，也不会串到别的会话；
  - Esc 同样可关闭（**有待发送的引用时，Esc 先取消引用**，再按才关窗）；
  - **对历史消息「回复 / 引用」**（2026-10-13 加）：悬停任意消息气泡即出现两个小按钮——
    **回复**＝"我针对这一段说，请就它作答"，**引用**＝"把这一段作为背景参考"。
    选中后输入框上方出现引用条（可取消），发出的消息在该条历史之后带着引用块。
    拼装只有 `web/src/quote.ts` 一份实现，格式为:
    `【回复此条】（你说的）` + `> 引用原文` + 空行 + 正文。
    于是**任务流水与会话文件里记的就是模型真正收到的**（回溯时能看出这条是针对哪句说的），
    刷新后 `parseQuoted` 再把它渲染回引用块。引用原文超 1500 字会截断——
    历史本来就在上下文里，引用只是明确"指向哪一条"，不是把原文再喂一遍。
- **过程可见**：assistant 的 `toolCall` 与 `thinking` 收在答复正文**上方**的「执行过程」里——**默认收起**（标题给概览：`bash×2 · 思考×3`），点击**展开看完整内容**（思考全文、工具完整参数，不做截断；过长时容器内滚动）。
- **会话列表**：每行有**重命名**与**清空**两个动作，删除固定在行**最右端**（与它们拉开距离，避免误点）；默认会话不出现删除按钮（它删了会被重建，只能用清空）。

### 8.3 定时任务的产出归档

定时任务（以及 API / 事件触发）**每次执行都新开一个会话**：

- 会话名形如 `定时·<任务名> MM-DD HH:mm`；
- 提问、答复、工具步骤、token 与费用全部落在该会话里，回看即知"这一次跑出了什么"；
- 不会把默认会话的上下文冲乱。

配套约束：**任务增删改后必须重载调度器**——已注册的定时器不会因为 `automations.json` 变化而停止（否则会出现"删掉的任务还在跑"）。网关在 create / delete / toggle 后会自动 `reloadScheduler()`。
- **头像**：在「Agent 设置 → 头像」上传；前端自动裁成方形并缩放到 256×256 后上传 PNG，与档案目录解耦存放于 `data/avatars/`——因此纳管的 Pi 员工同样可以有头像。
- **使用统计**：直接聚合 pi 原生会话文件中的 `usage`，给出**热力图**（绿色 = 当日有工作）以及**今日 / 近 7 天 / 近 30 天**的 token 消耗与费用。平台不重复记账，CLI、看板与外部渠道产生的消耗一视同仁。
- **会话费用**：每个会话都在**列表行**与**对话窗底部**显示累计 token 与费用，并可按模型拆分（悬停看明细）。费用**按模型单价计算**，而不是直接采信记录值。

### 8.2 模型价格表

费用口径由价格表决定，优先级如下（高 → 低）：

1. `data/pricing.json` —— 平台侧覆盖文件，可手工调整单价；
2. pi 的模型目录 `~/.pi/agent/models-store.json`、`models.json`（其中的 `cost` 字段）。

单价单位统一为 **USD / 1M tokens**（`input` / `output` / `cacheRead` / `cacheWrite`）。价格表未覆盖的模型会回退到 pi 记录的 `cost`，并在界面上标注"按 pi 记录计费"。初始 `pricing.json` 由本机历史计费反推生成，只补充 pi 未收录的模型。

## 九、已知限制与路线图

### 已知限制

- Docker 未运行时，`sandbox: true` 的员工无法执行 bash（其余能力不受影响）；
- memory-server 未启动不影响执行，仅跨会话记忆不生效；
- 记忆**召回快、写入慢**是刻意的不对称（2026-11-11）：召回用的嵌入模型**常驻显存**（LM Studio 的 JIT 模型每次请求后就被 TTL 卸载，导致每次召回重新加载 = 0.55s；常驻后 0.05s 左右，快 7~10 倍）；写入侧**攒够 3000 token 才启动抽取**（`extract.min_tokens`，另配 `max_wait_seconds: 1800` 兜底），并且**抽取前显式加载一次模型**（`load_ttl_seconds: 600`，用完自动卸载）。实测依据与排障见 `vendor/multi-pi-memory/README.md`；
- 记忆的**嵌入失败不再静默降级**（2026-10-11）：以前失败会写 hash 向量（无语义、永远搜不到、外部看不出来），
  实测库里真躺了 3 条；现在重试 3 次（含 HTTP 探活唤醒），仍失败则写入存 `embedding=NULL`（记忆仍在、暂时不可召回）、
  抽取整批重试，绝不再写垃圾。健康口：`GET :8971/api/status` 的 `embedding.ok` 与 `embedding.degraded_rows`，
  补算用 `POST :8971/api/reembed`。`/api/health` 的 `loaded` 也改成 HTTP 探活（`lms ps` 不列嵌入模型且会挂，恒报 false）；
- 记忆归属分**三档**：私有（`project == WAKER_ID`，本岗位积累）、共享（`project == shared`，用户画像与本机环境事实，所有员工可见）、知识库（`source == knowledge`，团队文档）。共享档只走显式 `memory_save(scope="shared")`，不按类别自动分流——类别本身不可靠（实测一条技术决策会被抽成 `fact`，而 `fact` 里「用户是内容创作者」与「某项目接口返回 4 个字段」混在一起）。`namespace` 为空的存量记忆**不对任何员工召回**，反之隔离一旦被绕过（如某处没注入 `WAKER_ID`），这批存量会无差别灌进每个人（详见 `vendor/multi-pi-memory/README.md`）；
- Group 多员工编排**暂不使用**：代码已实现（成员并行 + Leader 汇总 + 主修改者唯一校验），但未接任何入口（无 CLI / 无 HTTP / 看板无界面），`data/groups.json` 从未创建。有协作场景时再接 `waker group run`；
- Pi 侧 agent **默认不纳管**（`config.piAgents=false`）：没导入的 id 对平台等于不存在——看板名册里不出现、`waker say <piId>` 报"未找到员工"。要收编走 `waker import`，要回到"全部可见"就 `waker config piAgents on`；
- **部分文档的评论区不允许回复**（飞书返回 `1069302`，文案指向文档的评论设置/发布状态）。2026-10-11 实测确认**与平台参数无关**：用顶层 `comment_id` 直接打飞书接口得到同一错误码，传二级 `reply_id` 则是 `1069307 不存在`；且连"回复机器人自己新建的评论"也被拒。**同一文档的新建评论接口是通的**，所以平台现在会先"新开一条评论并 @ 提问者"，再退到私聊；
- **飞书文档评论里没有 Markdown**（评论接口只接受纯文本），所以走评论区那条路的答案仍是带 `**` 的原文；私聊/会话回帖那条路才有卡片渲染；
- Pi 侧扩展的 **`feishu_send_message` 仍发纯文本**（那是用户自己的 Pi 资产，没动）：员工**主动**发消息过去没有卡片渲染，需要时用 `feishu_request` 手动发 `msg_type=interactive`；平台自己的回帖/私聊路径已全部走卡片；
- 记忆**不做自动 TTL**（2026-10-11 决定）：误删长期记忆不可接受，改用抽取侧约束 + `waker memory review` 人工审阅；
- **复制记忆**（把某批记忆复制到另一个 waker id 名下，如接管某个 agent 时给它补一份私有记忆）会在库里留下同文两份。检索侧已按**内容去重**（保留分数最高的那份），重复条目**不占注入位**——实测「内容发布标准」一问，去重前 5 个名额被重复吃掉 2 个，去重后 5 个全部有效；
- `waker chat` 交互期间会**一直持有**该会话的锁：此时看板对同一会话的请求会排队，最长等 10 分钟后以明确报错结束（换一个会话即可继续）；
- **防睡眠只防"空闲睡眠"，不防合盖**（2026-10-11）：任务运行期间平台持有
  `caffeinate -i -w <pi pid>` 断言（随 pi 进程退出自动解除，`pmset -g assertions` 可验证），
  但**合盖睡眠在电池供电下系统强制执行**，软件拦不住；要合盖跑就接电源 + 外接显示器（苹果的合盖模式）。
  全局开关：`WAKER_NO_CAFFEINATE=1`。另外它**不能把已睡着的机器唤醒**——定时任务落在睡眠窗口里就会错过，
  需要的话用 `pmset repeat` 设定时唤醒（系统级，得自己管理）；
- **两套防睡眠别混为一谈**（2026-10-20 补）：上面说的是**任务期间**的临时断言（随 pi 进程起落）；
  另有「工具 → 系统」里的**常驻开关**（`config.preventSleep`，`waker power on|off`），
  它持一条 `caffeinate -i -s -w <看板 pid>` 的断言，直到你关掉或看板进程停止——两者互不影响。
  合盖防不住这条限制对两者同样成立；断言绑的是看板 pid，所以不会留下孤儿进程；
- Channel 层目前只实现 **飞书**；微信 / Discord / 钉钉**暂不做**（2026-10-11 决定，接口已留好，有需求再接）；
- 渠道长连接与旧 `feishu-bot` 互斥：同一 appId 只能一方连接；
- 用量统计**只读聚合 pi 会话文件**，价格表未覆盖的模型回退到 pi 记录的 cost（界面标注"按 pi 记录计费"）。
