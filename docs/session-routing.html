revolver · session routing

一句话进来，它怎么找到该去的那个会话？

飞书里看到的"切换话题"，本质是给每条消息挑一个 session（弹巢）。判定只用两个东西： 这句和每个会话有多像（向量），以及像到什么程度才值得动用户的指针（阈值 + 闸门）。 下面这张图是当前线上（2.3.0）的真实顺序，不是示意。

→判定链路（自上而下）

① 窗口 → 指针 conversations.json
飞书私聊映射成 feishu:u_，群聊按发言人再分一层。 每个 key 记一个 activeSessionId：这句话默认落在它指向的会话里。 会话被删会自动回落到主会话。
② 三道"先别判"的拦截
有待答的询问卡 → 先按用户的回答处理（1..N / N+1 / N+2）优先
句首「新话题 / 换个话题」→ 直接开新弹巢，不调模型 确定性
带附件的消息 → 直接落当前会话（卡片只存文本，切过去后图就没了）绕过
③ 候选池 = 该员工全部会话（不再按活跃度截断）
不只是"这个窗口装过的"。否则在网页里聊过的话题，飞书里永远找不回来。
以前按最近活跃取前 8，会把"很久没动但正是这个"的会话切掉；现在全部参与排序， 由④的索引打分决定谁进前 3。
④ 语义召回：全量索引，块间取最大 sessionIndex.ts
后台把每个会话的每条用户消息（外加标题、会话卡）算好向量落盘；查询时只 embed 这一句， 在已算好的向量里算余弦（毫秒级）。首次建库 415 块 / 7.5 秒，之后增量追加。
每个会话取最像的那块 vmax，得到 sActive（当前会话）与 sBest（最像的旧会话）。 索引不完整或服务挂掉时，自动退回 2.2.9 的现场切块 / 词面判定。
⑤ 候选怎么排序：vmax 为主，去背景做修正（不求和）
每个会话算四个数：vmax（最像那块）、bg（该会话全部块的平均，背景）、 support（去重后 top-3 均值）、lex（标题命中）。
S = 0.6(vmax−bg) + 0.25(support−bg) + 0.15·lex —— 只用于排序。不求和：一个 169 条的会话凑三个 0.55 会压过逐字命中的 1.00。
⑥ 阈值判定：先"继续"，再"切回"，最后才"新话题"
错误代价不对等，所以顺序不能反：误继续只是少省点 token，误切会让你"觉得它忘了刚才"。
条件结论
sActive ≥ 0.58继续在当前会话
sBest ≥ 0.60 且比 sActive 高 ≥ 0.08切回最像的旧会话
闲置 ≥ 8h 且两边都不像（< 0.45）新话题
其它模糊 → 留在当前（低置信不打扰）
⑥ 强匹配短路：只发一个标题/专名时不再问模型
sBest ≥ 0.95 且领先当前 ≥ 0.25 → 直接判切换。 这类输入（例如只发「esp32-cam」）向量分是 1.0，但小模型读不懂。
⑦ 仲裁（laya）：只能"在语义认可时点头" topicArbiter.ts
候选先按相似度重排，取前 5 交给决策模型，它答 current / c1..c5 / next。
它的 switch 必须过三关：目标在语义前 3、离第一名 ≤ 0.05、领先当前 ≥ 0.05。 不过就丢弃（记账本里是 verdict: drop）。实测 8 次语义可用的 switch 里，7 次被这条挡下。
⑧ 置信门槛 + 询问门
决策置信 < 0.5 → 静默在当前会话作答，不问也不切。
否则看配额：ask: always → 发卡；autoSwitch → 直接切并告知；拒绝 2 次 → stay（不切）。 用户自己切过一次，拒绝计数清零。
⑨ 询问卡：3 个候选 + 两个出口 + 一个负样本
「切到《A》」「切到《B》」「切到《C》」／「留在《当前》」／「看看全部话题」／「以上都不是」。 点候选 = 带原话切过去并作答；「留在」= 拒绝一次；「全部话题」= 可展开列表； 「以上都不是」= 明确告诉系统候选排序全错（最有价值的负样本，用来调权重）。
⑩ 落指针 + 留痕（决策账本）
setActive 改指针，旧会话打 transferredTo。 这条消息在目标会话里作答，用户不用重说；同时写一行决策账本（见右下）。

≡为什么还会找错（已知短板）

短板后果
嵌入判别力有限：同义改写只差 0.04阈值只能二选一：少切或误切
laya 对短消息输出近似均匀（confidence 0.06~0.4）只能让它否决/确认，不能单独决定
会话卡质量决定候选区分度没卡的会话只剩标题 + 1 块抽样
阈值是全局常量（0.58 / 0.60 / 0.08 / 8h）不随员工、语言、消息长度自适应
记忆库只进 prompt，不参与路由"我记得这件事"帮不上"这句该进哪个会话"

#决策账本：一次推荐的四条事件（data/decisions.jsonl）

一个 id 串起一次完整的推荐闭环。只记"判了什么"是不够的 —— 要判断准不准、该不该问，必须知道用户看到了哪几个候选、点了哪个、最后落在哪。

route

  • message / messageLength
  • active（id + 名字）
  • semantic：model / regime / active / best
  • index：used / scored（走没走全量索引）
  • candidates[]：rank / id / name / score
  • strongMatch
  • arbiter：model / ms / action / target / verdict / raw（含各项概率）
  • decision：action / target / confidence / reason
  • askGate：gate / ask / autoSwitch / rejectLimit / rejectStreak

ask

  • shown[]：用户实际看到的 3 条（顺序 = 按钮顺序）
  • proposed / proposedTarget
  • cardButtons

answer

  • kind：candidate / stay / list / none / text / timeout
  • sid：选了哪条
  • via：button / number / text-yes
  • typed：直接说别的内容（负样本）
  • latencyMs：发卡到回复的间隔

final

  • kind：switch / new / stay / list
  • sessionId / sessionName：最后答在哪
  • why：continue / low-confidence / ask-accepted / ask-rejected / auto-switch / manual-pick …

怎么用（按 id 串起来）

node -e '
const fs = require("fs");
const rows = fs.readFileSync("data/decisions.jsonl","utf8")
  .trim().split("\n").map(JSON.parse);
const by = new Map();
for (const r of rows) (by.get(r.id) ?? by.set(r.id, []).get(r.id)).push(r);
for (const [id, evts] of by) {
  const route = evts.find(e => e.evt === "route");
  const answer = evts.find(e => e.evt === "answer");
  const final  = evts.find(e => e.evt === "final");
  if (!route) continue;
  console.log(id,
    route.decision.action + "→" + (final?.kind ?? "?"),
    "答复:" + (answer?.kind ?? "none"),
    "候选:" + route.candidates.slice(0,3).map(c => c.name + ":" + c.score).join(" | "));
}
'
